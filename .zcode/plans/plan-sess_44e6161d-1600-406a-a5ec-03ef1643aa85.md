# Sprint H — Notification Center Implementation Plan

## Pre-Sprint Audit Summary (what exists vs. gaps)

**Already exists (reuse, do NOT duplicate):**
- Domain: `Notification`, `NotificationPreference` (shouldDeliver logic), `NotificationDelivery` (PENDING/SENT/FAILED/READ, MAX_DELIVERY_ATTEMPTS=3) in `apps/notification-service/src/domain/`
- Tables: `notification.notifications` (unique `(tenant_id,user_id,source_type,source_id)` idempotency), `notification_preferences`, `notification_deliveries` — all RLS-enforced
- REST bell API: `notifications.controller.ts` (list/unread-count/read/read-all/preferences) gated by `notification.alert.read`
- WS gateway emitting `notification.new` to `tenant:<tid>:notifications` room (port 3010)
- `ChannelProvider` abstraction: WebSocketChannel, InAppChannel, EmailChannel (nodemailer, SMTP env-gated, `getUserEmail` is a **stub returning null**)
- Frontend: complete data layer (`notification.api.ts`, `queryKeys.notifications`), built-but-unmounted `NotificationBell.tsx`, `useRealtimeSocket`/`useAlarmRealtime` hooks, fa/en i18n infra, MUI + React Query + Vitest
- Kafka: consumer on `fleetvision.tracking.events` with envelope validation, bounded retry, `<topic>.dlq` DLQ, Redis eventId idempotency; alarm evaluator → `dispatchAlarm()`
- Users live in `iam.users` (identity-service) with `email`; **no phone column**; no cross-service user-lookup client

**Gaps Sprint H must close:**
1. Recipient resolution (dispatch is broadcast `userId:null`; prefs never consulted; email lookup stubbed)
2. Per-user notification fan-out with per-user read state + per-user WS rooms
3. SMS/PUSH provider abstractions (config-gated, honest DISABLED status)
4. Safe templates + fa/en i18n (title/body currently string-built inline)
5. Durable delivery retry (currently in-memory `setTimeout` — lost on restart; no concurrency claim)
6. Rate limiting / storm protection (none)
7. API: detail endpoint, filters (type/vehicle/date/severity), delivery status
8. Frontend: mount bell, realtime updates (currently 30s polling only), Notification Center page, preferences UI, i18n keys
9. New RBAC permissions (`notification.read`, `notification.read.all`, `notification.preference.read/write`)
10. Metrics, provider health, Mailpit dev container, Playwright browser E2E, docs

## Backend — apps/notification-service

### 1. Config (`src/config/notification.config.ts`)
Add zod-validated vars: `NOTIF_SMS_ENABLED` (default false), `NOTIF_PUSH_ENABLED` (default false), `NOTIF_MAX_DELIVERY_ATTEMPTS` (3), `NOTIF_RETRY_BASE_MS` (2000), `NOTIF_RETRY_WORKER_INTERVAL_MS` (5000), `NOTIF_RATE_LIMIT_PER_MIN` (30/tenant/user/channel), `NOTIF_DEFAULT_LOCALE` ('en'). Existing `NOTIF_SMTP_*` kept; email channel enabled only when SMTP configured.

### 2. Domain extensions
- `notification-types.ts`: add `NotificationPriority` (LOW/NORMAL/HIGH/URGENT) + deterministic `severityToPriority` mapping (critical→urgent, high→high, normal→normal, low→low); document mapping
- `notification.ts`: add `eventType`, `vehicleId`, `metadata`, `priority` props
- `notification-delivery.ts`: add `nextAttemptAt`, `provider`, `providerMessageId`, `errorCode`; add `DELIVERED` status (only set when provider confirms — otherwise SENT = accepted); transient-vs-permanent error classification helper
- New `notification-template.ts`: safe `{{var}}` regex interpolation (no executable code)

### 3. Migration `20260816100000_extend_notification_center.js`
- `notifications`: + `event_type varchar(64)`, `vehicle_id uuid null`, `metadata jsonb`, `priority checkIn(low,normal,high,urgent)`; indexes `(tenant_id, event_type, created_at desc)`, `(tenant_id, vehicle_id, created_at desc)`
- `notification_deliveries`: + `next_attempt_at timestamptz null`, `provider varchar(32)`, `provider_message_id text`, `error_code varchar(64)`; index `(tenant_id, status, next_attempt_at)` for the retry sweeper
- Same RLS hardening pattern as existing migrations; forward-only

### 4. Recipient resolution (NEW `application/recipient-resolver.service.ts` + `infrastructure/persistence/user-directory.ts`)
Read-only `withPlatformContext` query on `iam.users` (status=active, by tenant) → `{userId, email, displayName}`. Trusted backend data only — never trusts alarm payloads for identity. Short Redis TTL cache. No new fleet-membership model (none exists — spec §19).

### 5. Templates + i18n (NEW `application/templates/`)
Registry keyed by alarm/event type with `en` + `fa` title/body using `{{vehicleName}}`, `{{speed}}`, `{{speedLimit}}`, `{{geofenceName}}`, `{{occurredAt}}` etc. from whitelisted server-side context. Fallback to alarm message when no template. Locale from user preference → `NOTIF_DEFAULT_LOCALE`.

### 6. Dispatcher refactor (`notification-dispatcher.service.ts`)
Replace broadcast with per-user flow:
1. Alarm → event type → template render (locale)
2. RecipientResolver → active tenant users
3. Per user: `getOrDefault` preference → enabled channels ∩ configured providers (channel registry)
4. Rate limiter check (Redis sliding window per tenant/user/channel) — skip + `notifications_rate_limited` metric
5. Create per-user notification (idempotent via existing unique constraint — Kafka redelivery safe, spec §17)
6. Per enabled channel: create PENDING delivery → immediate attempt; failures go to durable retry worker (setTimeout retry removed)
7. All channels disabled → no row, logged + counted (no retry loops)
Dedup policy: `ON_OPEN` only (current, deterministic); documented. No re-evaluation of alarm conditions.

### 7. Provider registry (`application/channels/provider-registry.ts`)
Config-driven channel→provider map with `status(): CONFIGURED | DISABLED`:
- `IN_APP`/websocket → existing WebSocketChannel (emits to **new** `user:<tid>:<uid>` room when userId set, else tenant room)
- `EMAIL` → existing nodemailer EmailChannel, wired to real `getUserEmail` via UserDirectory (removes the null stub)
- `SMS` → `SmsProvider` abstraction returning DISABLED when `NOTIF_SMS_ENABLED=false` / no provider config — never fake endpoints
- `PUSH` → `PushProvider` abstraction + `push_device_tokens` persistence-ready interface, DISABLED until a provider is configured
No `if email then SMTP` logic in business code.

### 8. Durable retry worker (NEW `application/delivery-retry-worker.service.ts`)
Interval poll of `notification_deliveries` (PENDING/FAILED, `next_attempt_at <= now()`), claim via `SELECT … FOR UPDATE SKIP LOCKED` (multi-worker safe, spec §53), exponential backoff `base * 2^attempts`, bounded by `NOTIF_MAX_DELIVERY_ATTEMPTS`, permanent errors (invalid email/phone/token, provider rejection) fail fast, exhausted retries → final FAILED + DLQ-style forensic log entry. Survives restart.

### 9. Rate limiter (NEW `infrastructure/cache/notification-rate-limiter.ts`)
Redis INCR+EXPIRE window per `tenant:user:channel` — storm protection for flapping devices.

### 10. WS gateway (`alarm-realtime.gateway.ts`)
Add allowed room `user:<tid>:<uid>` validated against the JWT principal (only the authorized user's targeted notifications reach them — spec §39/45).

### 11. API (`notifications.controller.ts` + DTOs)
- `GET /notifications/:id` — detail + delivery attempts timeline
- List filters: `eventType`, `severity`, `vehicleId`, `from`, `to`, `unreadOnly`; keep cursor pagination
- `GET /notifications/deliveries/:id` (or nested) for attempt history
- Preferences endpoints unchanged in path (existing convention) but permissions switched to new dedicated ones; admin tenant-wide history via `notification.read.all` + `scope=all`
- Provider health exposed via existing health controller: per-channel CONFIGURED/DISABLED, no secrets

### 12. Observability (`packages/observability/src/metrics/telemetry-metrics.ts`)
New bounded-label counters: `notifications_created/dispatched/sent/failed/retried/rate_limited/deduplicated_total` + `notification_provider_total{channel,result}`. Structured logs with tenantId/notificationId/alarmId/userId/channel/provider/attempt/correlationId (existing pino + correlation-context).
